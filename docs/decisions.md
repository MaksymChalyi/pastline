## 8. Серверна сесія і CSRF замість JWT

*12.11*

**Рішення.** 6.2: серверна сесія в HttpOnly cookie (SameSite=Lax) + CSRF-токен у cookie XSRF-TOKEN, BCrypt, однакова відповідь на невідомий email і неправильний пароль

**Чому.** сесію можна інвалідувати на сервері, токен не лежить у localStorage, фронт і бек на одному домені

**Відкинуті альтернативи.** JWT у localStorage

**Питання → відповідь.** "Чому не JWT?" → для одного SPA на тому ж домені сесія простіша й безпечніша: logout миттєвий, XSS не викраде токен

## 9. JWT для мобільного клієнта — пізніше

*12.11*

**Рішення.** JWT/Bearer для мобільного клієнта — після диплома, додається поруч із сесією в модулі `auth`

**Чому.** до 27.11 мобільного клієнта немає; решта модулів залежить лише від `AuthenticatedUser.id`, тож зміна локальна

**Відкинуті альтернативи.** JWT уже зараз замість сесії

**Питання → відповідь.** "А якщо буде мобільний застосунок?" → окремий ланцюжок фільтрів з Bearer-токеном поруч із сесією для вебу

## 10. Власність записів і дедуплікація

*12.11*

**Рішення.** 6.3: власник запису як `user_id` (без `@ManyToOne` на `User`), кожен запит репозиторію з `userId` у SQL, чужий запис → 404; дублікат = `user_id + entry_date + sha256(нормалізований текст)` → 409

**Чому.** модуль `journal` не залежить від сутностей `auth`; 404 не розкриває існування чужого id; той самий ключ дедуплікації використає імпорт 6.4

**Відкинуті альтернативи.** перевірка власника в Java після `findById`; 403 для чужого запису

**Питання → відповідь.** "Як гарантуєте ізоляцію?" → фільтр `user_id` у кожному SQL-запиті + тест: B отримує 404 на GET/PUT/DELETE запису A

## 11. Імпорт: перша версія

*12.11*

**Рішення.** 6.4: імпорт без спільної транзакції (кожен запис окремо через `JournalService.create`), дедуплікація в БД і всередині файлу, `dryRun=true` за замовчуванням; корпус генерує один Java-файл із seed 42, `corpus.json` + SHA-256, без CRLF-перетворення в git

**Чому.** помилка одного запису не відкочує решту; повторний імпорт додає 0; валідація і хешування в одному місці (модуль journal); байт-у-байт відтворюваний корпус є доказом для експериментів

**Відкинуті альтернативи.** одна транзакція на файл (все або нічого); Python-скрипт для корпусу; ручна вибірка записів

**Питання → відповідь.** "Як відтворити експеримент?" → `java scripts/generate-corpus/GenerateCorpus.java` дає той самий файл, тест звіряє SHA-256 і імпортує всі 520 записів

## 12. Лексичний пошук на повнотекстовому пошуку PostgreSQL

*12.11*

**Рішення.** 6.5: generated-колонка `search_vector` (`to_tsvector('simple', title + content)`) з GIN-індексом, `websearch_to_tsquery` + `ts_rank`, native SQL через `NamedParameterJdbcTemplate`, один ендпоінт `/search?mode=` для всіх режимів

**Чому.** вектор оновлює сама БД, без коду в Java; `simple`, бо українського стемера немає; ввід користувача не ламає запит; режими порівнюються одним API

**Відкинуті альтернативи.** тригер або оновлення вектора в сервісі; `plainto_tsquery`; пошук за префіксом; окремий ендпоінт на режим

**Питання → відповідь.** "Чому лексичний пошук не знаходить 'пробіжку' за 'пробіжка'?" → без стемінгу форми слова різні токени; це і є гіпотеза, яку перевіряє порівняння з семантичним пошуком

## 13. Семантичний пошук і власна таблиця векторів

*12.11*

**Рішення.** 6.6: власна таблиця `entry_embeddings` (vector(768), model, content_hash, READY/FAILED) без PENDING; фоновий `EmbeddingIndexer` (`@Scheduled`, пачки по 32) сам знаходить записи без актуального вектора за `content_hash`; порт `EmbeddingModelPort` з адаптером Spring AI/Ollama; префікси EmbeddingGemma (`task: search result | query:` / `title: … | text:`); exact `<=>` з фільтром `user_id`; недоступна модель → 503, запис чекає, а не FAILED

**Чому.** journal не знає про ембедінги; імпорт 520 записів не блокує HTTP; після перезапуску індексація продовжується; застарілий вектор ніколи не потрапляє у видачу; модель замінюється без змін у search; у тестах детермінований фейк

**Відкинуті альтернативи.** синхронний виклик моделі в CRUD; `@TransactionalEventListener` + `@Async`; Spring AI `PgVectorStore`; HNSW; тести з реальною Ollama

**Питання → відповідь.** "Що, якщо запис відредагували?" → змінюється content_hash, вектор стає застарілим, пошук його пропускає, індексатор перераховує за кілька секунд; `pendingCount` у відповіді показує, скільки ще не проіндексовано

## 14. Імпорт: прискорення (Persistable, три кроки, пакетна вставка)

*12.11*

**Рішення.** 6.4 (виправлення після Gate 1): `JournalEntry implements Persistable` (persist замість merge), імпорт у 3 кроки: перевірка в пам'яті → ключі з БД одним запитом → вставка пачками по 100 (JDBC batch, `reWriteBatchedInserts`)

**Чому.** на Gate 1 імпорт 520 записів ішов 4+ хв: на кожен запис окремі транзакції, exists і merge (SELECT перед INSERT через призначений UUID)

**Відкинуті альтернативи.** транзакція на кожен запис; одна транзакція на весь файл; асинхронний імпорт із прогресом

**Питання → відповідь.** "Чому save() робив SELECT?" → Spring Data вважає сутність з непорожнім id наявною і викликає merge; Persistable.isNew() каже, що запис новий

## 15. Гібридний пошук через RRF

*12.11*

**Рішення.** 6.7: `mode=hybrid` = RRF над top-50 lexical і top-50 semantic, `score = Σ 1/(k + rank)`, k=60 у `pastline.search.rrf-k`; `RrfFusion` чиста функція; `debug=true` дає `lexicalRank`/`semanticRank`/`rrfScore`; недоступна модель → 503 без відкату на lexical

**Чому.** бали режимів несумісні (ts_rank ~0.06, косинус ~0.4), RRF працює лише з рангами; k як параметр дозволяє перевірити чутливість у бенчмарку; debug пояснює кожну позицію для розділу 3

**Відкинуті альтернативи.** зважена сума нормалізованих балів (потребує підбору ваг і нормалізації); тихий fallback на lexical

**Питання → відповідь.** "Чому RRF, а не середнє балів?" → шкали балів різні й нелінійні, ранги порівнювані завжди; k=60 з оригінальної роботи Cormack et al. (2009), на наборі запитів не підбиралося (абляції k не було)

## 16. Набір запитів і еталон релевантності

*12.11*

**Рішення.** Набір запитів queries-v1: еталон = записи, що містять цільове речення корпусу (128 речень `T001`-`T128`, еквіваленти іншою мовою додаються); 4 типи (exact, wordform, paraphrase, crosslingual); джерела `claude` (42), `chatgpt` і `deepseek` (по 25 за однаковим промптом), `author` (10) замість трьох людей

**Чому.** еталон обчислюється з корпусу механічно, без суб'єктивної розмітки; різні автори запитів зменшують упередженість одного джерела; метрики рахуються загалом і окремо за джерелом і типом

**Відкинуті альтернативи.** мітка topic як еталон (55-94 релевантних на запит, метрики неінформативні); ручна розмітка релевантності; запити лише від одного автора

**Питання → відповідь.** "Хто складав запити?" → автор і три LLM з фіксованим промптом, джерело кожного запиту записане; обмеження: не реальні користувачі, це вказано в розділі 3

## 17. Бенчмарк як профіль застосунку

*12.11*

**Рішення.** 6.9: бенчмарк як профіль `benchmark` того самого застосунку (без веб-сервера): окремий користувач, імпорт корпусу, синхронна індексація, `SearchService` напряму; метрики Hit@1/5/10, MRR@10, Recall@10 з першого прогону, затримка p50/p95 з 5 прогрівів + 20 повторів; JSON-звіт з хешами корпусу і файлів запитів, зведення загалом / за типом / за джерелом

**Чому.** одна команда дає відтворюваний результат; той самий код пошуку, що й у застосунку; хеші входу доводять, на чому саме отримано числа; розріз за типом і джерелом відповідає на питання методики

**Відкинуті альтернативи.** окремий скрипт через HTTP (міряє мережу і cookie, не пошук); ручні заміри; лише загальні середні

**Питання → відповідь.** "Як отримано числа в таблиці?" → `mvnw spring-boot:run -Dspring-boot.run.profiles=benchmark`, звіт `docs/experiments/results/run-*.json` містить SHA-256 корпусу і запитів

## 18. Бенчмарк: 5 повторів і проміжний звіт

*14.11*

**Рішення.** 6.9 після першого прогону: 5 повторів замість 20; звіт перезаписується після кожного режиму; бенчмарк запускати від мережі з вимкненим сном

**Чому.** перший прогін: semantic ~0,65 с на запит (вектор запиту в Ollama на CPU), 42 запити × 25 = 12 хв на режим; ноутбук заснув посеред hybrid, звіт втрачено; зі ~100 запитами 20 повторів = ~1 год; 5 повторів дають ~500 вимірювань на режим, достатньо для p50/p95

**Відкинуті альтернативи.** 20 повторів за PLAN; кешування вектора запиту (міряло б не реальну затримку)

**Питання → відповідь.** "Чому 5 повторів?" → метрики якості детерміновані (один прогін), повтори потрібні лише для затримки; 5 × ~100 запитів = ~500 точок на режим

## 19. Абляція лексичного оператора AND / OR

*14.11*

**Рішення.** Абляція лексичного оператора: `pastline.search.lexical-operator=and|or` (за замовчуванням and), бенчмарк проганяється для обох; Recall@10 нормується на min(10, кількість релевантних)

**Чому.** повний прогін (102 запити): lexical з AND повернув результати лише на 11 запитів (усі exact), тож hybrid збігся з semantic і H3 неможливо перевірити; класичний лексичний пошук (BM25) працює через OR; у запитів 5–32 релевантних записи, і ненормований Recall@10 не міг сягнути 1

**Відкинуті альтернативи.** лише AND (baseline вийшов би штучно слабким); BM25-розширення PostgreSQL (нова залежність перед freeze); stop-word словник для 'simple' (відсікаю слова < 3 символів)

**Питання → відповідь.** "Чи не занижений лексичний baseline?" → виміряні обидва оператори, AND і OR; вплив оператора на hybrid показаний окремо

## 20. Результат абляції: у застосунку лишається AND

*14.11*

**Рішення.** Результат абляції: у застосунку лишається `and`; H3 не підтверджена; RRF не підлаштовується під набір запитів

**Чому.** OR підняв lexical (MRR@10 0,108 → 0,338), але hybrid з OR гірший за semantic (0,832 → 0,691; 27 запитів гірше, 3 краще): збіг одного частого слова («годин», «for», «керівник») ставить нерелевантні записи на верх лексичного списку, а RRF зважує обидва списки однаково; hybrid з AND = semantic, крім exact (Recall@10 0,955 → 0,973)

**Відкинуті альтернативи.** ваги RRF або k, підібрані на цьому ж наборі (окремого dev-набору немає, підгонка завищила б результат); OR за замовчуванням

**Питання → відповідь.** "Чому hybrid не кращий?" → без стемінгу лексичний сигнал або порожній (AND), або шумний (OR); зважений RRF і український стемер — future work

## 21. Ask Pastline і перевірка джерел

*14.11*

**Рішення.** 6.10: `POST /api/v1/ai/ask` → hybrid top-8 → записи з короткими id E1…E8 у тегах `<entry>` (кутові дужки екрануються) → qwen3:4b через `ChatModelPort` з вимкненим thinking → пост-валідація: речення лишається лише з посиланням на переданий id; без жодного перевіреного речення або на `NO_ANSWER` статус `NO_EVIDENCE`; без знайдених записів модель не викликається

**Чому.** мала модель перекручує UUID; правило «кожне речення має джерело» просто перевірити й пояснити; `removedSentences` у відповіді та сирий текст в `AskResult` потрібні для вимірювання H5; екранування не дає запису закрити свій тег і видати себе за інший запис

**Відкинуті альтернативи.** UUID у посиланнях; перевірка лише вигаданих id (речення без посилань лишались би); показ відповіді з попередженням замість відмови; LLM-суддя для перевірки фактів (ще одна модель, ще одне джерело помилок)

**Питання → відповідь.** "Що, як модель вигадає джерело?" → речення з id, якого не було в контексті, видаляється до показу; тест з «отруєною» відповіддю це перевіряє

## 22. Модель відповідей qwen3:4b-instruct

*14.11*

**Рішення.** Модель Ask Pastline: `qwen3:4b-instruct` замість `qwen3:4b`; ліміт відповіді 400 токенів, тайм-аут 300 с, без повторів Spring AI

**Чому.** `qwen3:4b` у реєстрі Ollama має той самий id, що `qwen3:4b-thinking-2507`: на CPU модель міркувала навіть із think=false, запит не вкладався у 5 хв; instruct-варіант того ж розміру відповідає без міркувань; повтор після тайм-ауту подвоював очікування

**Відкинуті альтернативи.** thinking-модель з більшим тайм-аутом (хвилини на відповідь); `qwen3:1.7b` (запасний варіант, якщо instruct теж повільний)

**Питання → відповідь.** "Чому не reasoning-модель?" → завдання — знайти й процитувати факт із 8 коротких записів; міркування на CPU коштують хвилини і не потрібні для перевірки джерел

## 23. Оцінка Ask Pastline (H5)

*14.11*

**Рішення.** Оцінка H5: `pastline.benchmark.task=ask` у профілі `benchmark`, набір `docs/experiments/ask-v1/questions.json` (20 питань: 15 з відповіддю з цілями з targets.json, 5 без відповіді; складені моделлю, `source: claude`, розкривається в методології), temperature 0; звіт JSON + CSV для ручної розмітки точності переказу; підготовка корпусу винесена в `CorpusPreparer`

**Чому.** сира відповідь моделі = «без перевірки», фінальна = «з перевіркою»: видно, скільки вигаданих [E#] модель дала і скільки відповідей змінила або заблокувала перевірка; ручна перевірка 4b-instruct показала помилку переказу (липень → серпень) при справжньому посиланні, тож точність переказу розмічається окремо

**Відкинуті альтернативи.** LLM-суддя для точності (ще одна модель і ще одне джерело помилок); кілька прогонів на питання (на CPU ~30 с кожен)

**Питання → відповідь.** "Що саме доводить H5?" → перевірка гарантовано прибирає вигадані джерела; чи точно модель переказує справжнє джерело, вона не гарантує, це показує ручна розмітка

## 24. Перший прогін оцінки H5

*14.11*

**Рішення.** Перший прогін H5 (qwen3:4b-instruct, 20 питань): H5 у вузькому формулюванні не перевірена — модель не вигадала жодного посилання (0 з 99), перевірці не було що прибирати; механізм підтверджено лише тестом з «отруєною» відповіддю. Звітую чесно, набір під результат не підганяю

**Чому.** 13/15 правильних відповідей, 5/5 правильних відмов, 0 відповідей без підстав; q14 — помилка пошуку (англійське питання, релевантний український запис не потрапив у контекст), q09 — обережна відмова (модель не пов'язала «державні облігації» з «ОВДП»); відповіді майже дослівно повторюють записи, бо корпус синтетичний і одне речення є в багатьох записах, звідси precision джерел 0,99 і цитування всіх 8 записів

**Відкинуті альтернативи.** підібрати складніші питання, щоб з'явились вигадки (підгонка набору під гіпотезу)

**Питання → відповідь.** "То перевірка джерел не потрібна?" → на цій моделі й корпусі вигадок не було, але перевірка — запобіжник із нульовою вартістю (мілісекунди); ручна перевірка вище знайшла помилку переказу дати, яку перевірка джерел не ловить

## 25. Онлайн-демо: Vercel + Render + Neon + Gemini

*14.11*

**Рішення.** Деплой онлайн-демо перенесено з 24.11 на 14.11 (рішення автора): Vercel (фронт, rewrite `/api/*` на бекенд — один домен для cookie) + Render Free (бекенд у Docker, профіль `cloud`) + Neon Free (PostgreSQL з pgvector) + Gemini API безкоштовного рівня замість Ollama: `gemini-embedding-001` з 768 вимірами (схема БД та сама) і `gemini-3.5-flash-lite` для відповідей (2.5 недоступні новим ключам); перемикач `pastline.ai.provider=ollama|gemini` за тими самими портами

**Чому.** $0 на місяць; Ollama не поміщається в 512 МБ Render; Neon не видаляє безкоштовну БД через 30 днів, на відміну від Render Postgres; Gemini-ембедінги дають 768 вимірів через параметр, тож міграції не потрібні; Vercel-rewrite робить API тим самим origin, без CORS і SameSite=None

**Відкинуті альтернативи.** AWS/EC2 (більше ручного налаштування мережі й HTTPS); Render Postgres (видаляється через 30 днів); OpenAI (платний ключ); Ollama на VPS (потрібно ≥8 ГБ RAM)

**Питання → відповідь.** "Онлайн-версія — це те, що міряли?" → ні: інша модель ембедінгів і відповідей, тому її числа в диплом не йдуть; безкоштовний Gemini використовує запити для покращення продуктів Google, тож онлайн лише синтетичний корпус, без справжніх записів
