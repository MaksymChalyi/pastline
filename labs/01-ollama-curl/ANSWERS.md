# Лаба 01: Ollama через curl

Дата: 10–11.11.2026 · Час: 3 год · Код: немає

**Середовище:** Windows, PowerShell, `curl.exe`, Ollama 0.40.15. Моделі: `qwen3:4b` для чату і `embeddinggemma` для embeddings. За `ollama ps`: `qwen3:4b` займає 3,2 ГБ, працює на `100% CPU` без GPU, контекст 4096 токенів.

## Мета

Побачити сирий HTTP-запит до локальної моделі і сиру відповідь без коду. Розібрати, з чого складається час відповіді, і як виглядає embedding. Результати — база для підрозділу 3.1.1 диплома.

## Як запустити

```powershell
ollama pull qwen3:4b
ollama pull embeddinggemma
ollama serve                      # окреме вікно, сервер на localhost:11434
cd labs/01-ollama-curl

Measure-Command { curl.exe http://localhost:11434/api/chat -H "Content-Type: application/json" -d "@chat.json" -o chat-out.json }
curl.exe http://localhost:11434/api/embed -H "Content-Type: application/json" -d "@embed.json" -o embed-out.json
```

| Частина команди | Що робить |
|---|---|
| `Measure-Command { }` | заміряє час виконання блоку з боку клієнта |
| `curl.exe` | справжній curl, бо `curl` у PowerShell є псевдонімом `Invoke-WebRequest` |
| `-H "Content-Type: application/json"` | заголовок: тіло запиту є JSON |
| `-d "@chat.json"` | тіло запиту з файлу (`@` означає «читати з файлу»); з `-d` curl робить POST |
| `-o chat-out.json` | зберегти відповідь у файл |

Запити:
- `chat.json` містить `model`, одне повідомлення `user` «Поясни семантичний пошук у трьох реченнях.», `stream`, а в останніх запусках ще `think`;
- `embed.json` містить три рядки: «Вивчав CompletableFuture», «Learned Java concurrency», «Купив квиток до Варшави».

## Як це працює

```text
POST /api/chat  →  завантаження моделі в RAM (лише якщо її ще там немає)  → load_duration
                →  обробка промпту                                         → prompt_eval_count / _duration
                →  генерація токенів по одному                             → eval_count / eval_duration
                ←  JSON: message.content (+ message.thinking), час у наносекундах

POST /api/embed →  один прохід моделі на кожен рядок, без генерації  ←  масив векторів
```

Модель — це локальний HTTP-сервер. Між запитами вона нічого не пам'ятає: бачить лише те, що прийшло в `messages`.

### Головна знахідка: `think: false` не вимикає роздуми `qwen3:4b`

Із `"think": false` окремого поля `message.thinking` у відповіді немає, але модель однаково міркує:
- міркування англійською потрапляють прямо в `message.content`;
- перед відповіддю стоїть закривальний тег `</think>` (без відкривального);
- лише останні ~400–480 символів — сама відповідь українською;
- у запуску 4 це 480 символів із 3713, тобто близько 87% згенерованого тексту не має цінності для користувача.

## Що пішло не так і як виправив

1. **Повторний запит повільніший за перший.** Справа не в завантаженні: `load_duration` упав майже до нуля. Модель щоразу генерує відповідь іншої довжини (528 проти 1977, 837 проти 2033 токенів), а час майже лінійно залежить від `eval_count`. Холодний і теплий старт порівнюю за `load_duration`, а не за `total_duration`.
2. **Без `-o` відповідь зникла.** curl сприйняв ім'я файлу як другу адресу (`Could not resolve host`), а відповідь на першу пішла в stdout, який `Measure-Command` не виводить. Виправив, додавши `-o`.
3. **`ollama stop` завис у стані `Stopping...`,** а новий запит чекав у черзі понад 5 хв. Допомогли зупинка процесу і ручний запуск `ollama serve`. Поки сервер не працював, curl повертав `Failed to connect ... Could not connect to server`. Ту саму помилку Java-клієнт має обробляти в лабі 02.
4. **`Failed to open chat.json`.** Запускав команду з кореня репозиторію: шлях `@chat.json` відносний до поточної папки.

## Висновки

1. Виклик LLM — звичайний HTTP POST із JSON. Застосунку потрібні таймаути, обробка помилок з'єднання і розбір JSON.
2. Холодний старт коштує 4,5–6,9 с на завантаження 3,2 ГБ моделі в RAM. Далі модель лишається в пам'яті (`load` ≈ 0,005 с), а промпт частково береться з кешу.
3. Основна частина часу — генерація: 5,2–6,5 токена/с на CPU. Одна відповідь на просте питання тривала від 87 до 393 с. Для інтерактивного «Запитати» в Pastline ця конфігурація непридатна без обмежень.
4. Довжина відповіді, а отже й час, від запуску до запуску змінюється в 2,4–3,7 раза. Час відповіді LLM непередбачуваний. Одиничні заміри не репрезентативні, у дипломі потрібні повтори і медіана.
5. `think: false` для `qwen3:4b` в Ollama 0.40.15 не прибирає міркувань, а змішує їх із відповіддю. Для генерації відповідей потрібна модель без режиму роздумів або видалення всього до `</think>` на сервері, хоча тоді марно витрачені токени і час нікуди не дінуться.
6. Embedding — це вектор із 768 чисел без генерації тексту. Після завантаження моделі розрахунок для трьох рядків зайняв ≈ 0,13 с, тож локальна індексація записів реальна.
7. Вектори `embeddinggemma` нормалізовані, тому cosine similarity для них дорівнює скалярному добутку (перевірю в лабі 03).

## Що це дає Pastline і диплому (підрозділ 3.1.1)

- **Обґрунтування архітектури.** Пошук (лексичний, семантичний, гібридний) не має залежати від генерації: embeddings швидкі, генерація повільна. LLM викликається лише для відповіді на питання.
- **Вимоги до Ask Pastline:**
  - відповідь показувати через streaming;
  - обмежувати довжину відповіді;
  - видаляти міркування з `content` на сервері або взяти модель без роздумів;
  - мати хмарний профіль для онлайн-демо.
- **Схема даних.** `vector(768)` у pgvector і метрика cosine. Якщо змінити embedding-модель, усі вектори доведеться перерахувати.
- **Контекст 4096 токенів у Ollama за замовчуванням** обмежує, скільки записів можна передати моделі в RAG. Це треба враховувати при виборі top-K або збільшувати `num_ctx`.
- **Загрози валідності:** заміри на CPU одного ноутбука, по одному запуску на режим, висока варіативність довжини відповіді.

## Питання, на які відповідаю без нотаток

**Чим масив чисел від `/api/embed` відрізняється від відповіді `/api/chat`?**
`/api/chat` генерує текст токен за токеном: це повільно, і результат щоразу інший. `/api/embed` робить один прохід по тексту і повертає вектор фіксованої довжини (768), який описує зміст. Текст із вектора не відновити. Вектори порівнюють між собою, щоб знаходити схожі за змістом тексти навіть без спільних слів.

**Чому модель не знає про мої записи, поки я їх не передам?**
Знання моделі зафіксовані у вагах під час навчання, а інференція їх не змінює. Модель бачить лише те, що надіслано в конкретному запиті, а «історію розмови» клієнт щоразу передає заново в `messages`. Щоб модель відповідала про мої записи, їх треба знайти пошуком і вставити в контекст запиту. Це і є RAG.

**Що означає `stream: true` для Java-клієнта?**
Відповідь приходить не одним JSON, а потоком рядків NDJSON. Клієнт має:
- читати їх построково, поки з'єднання відкрите (`BodyHandlers.ofLines()`);
- розбирати кожен рядок окремо;
- відокремлювати `thinking` від `content` і збирати текст;
- завершувати роботу на `done: true`;
- обробляти обрив на півдорозі.

Таймаут на всю відповідь тут не підходить, бо генерація триває хвилинами. Потрібні таймаут на з'єднання і таймаут на паузу між шматками.

**Чому перший запит повільніший?**
Ollama завантажує модель з диска в RAM (`load_duration` 4,46–6,89 с). Наступні запити йдуть до вже завантаженої моделі, доки вона не вивантажиться після простою.

**Теорія**

| Поняття | Коротко |
|---|---|
| LLM | нейромережа, яка передбачає наступний токен і так, токен за токеном, генерує текст |
| Inference | використання навченої моделі без зміни ваг; в Ollama це `prompt_eval` + `eval` |
| Токени | одиниці тексту для моделі (частина слова, слово, знак); час генерації пропорційний `eval_count` |
| Контекстне вікно | скільки токенів модель бачить за раз: запит, історія, вставлені записи і відповідь. В Ollama за замовчуванням 4096, хоча `qwen3` підтримує більше |
| Temperature | випадковість вибору наступного токена: нижча означає стабільніші відповіді. Для відповідей за записами — низька |
| Галюцинації | правдоподібні, але вигадані твердження; модель генерує текст, а не перевіряє факти. Тому в Pastline кожне твердження має посилання на запис, яке перевіряє код |
| Embedding | вектор фіксованої довжини, що представляє зміст тексту; близькі за змістом тексти мають близькі вектори |
| Cosine similarity | `Σ(aᵢ·bᵢ) / (‖a‖·‖b‖)`: 1 — однаковий напрям, 0 — незалежні, −1 — протилежні; для нормалізованих векторів дорівнює скалярному добутку |
| RAG | знайти релевантні записи пошуком, передати їх моделі разом із питанням, відповісти лише на їх основі з посиланнями |
| Чому RAG не навчає модель | ваги не змінюються; записи потрапляють лише в контекст одного запиту, їх можна будь-коли змінити чи видалити, і видно, на що спирається відповідь |
