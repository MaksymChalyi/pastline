# Лаба 02: Java HttpClient → Ollama

Дата: 11.11.2026 · Час: ~4,5 год

**Середовище:** Java 21 (Corretto 21.0.10), Maven, IntelliJ IDEA 2024.3. Залежності: Jackson 2.23.0, JUnit 6.1.3, Surefire 3.6.1. Без Spring. Ollama 0.40.15, модель `qwen3:4b` на CPU.

## Мета

Хотів переконатися, що виклик LLM із застосунку — це звичайний HTTP-запит із JSON, який може впасти через таймаут, недоступний сервер чи поганий JSON, і навчитися все це обробляти без фреймворку.

## Як запустити

```powershell
cd labs/02-java-http-client
mvn test                                           # тести, Ollama не потрібна
ollama serve                                       # в окремому вікні
mvn -q compile exec:java "-Dexec.mainClass=lab.Main"
```

Модель можна змінити змінною оточення `OLLAMA_MODEL`, за замовчуванням `qwen3:4b`.

## Як це працює

```text
Main ──▶ OllamaClient.chat(model, history)
           ├─ ChatRequest (record) ──Jackson──▶ JSON
           ├─ HttpClient.send(POST /api/chat)        connectTimeout 5 с, request timeout 10 хв
           ├─ статус ≠ 2xx                            → OllamaException("HTTP 500: ...")
           ├─ HttpConnectTimeoutException             → "Не вдалося під'єднатися за 5 с"
           ├─ HttpTimeoutException                    → "Ollama не відповіла за N с"
           ├─ ConnectException                        → "Ollama недоступна ... Чи запущено ollama serve?"
           └─ JSON ──Jackson──▶ ChatResponse → message.content
Main: відповідь додається в history як "assistant", друге питання її бачить
```

Структура:
- `lab/OllamaClient.java` — один `HttpClient` на весь час життя об'єкта, два таймаути, перетворення всіх збоїв на `OllamaException`;
- `lab/OllamaException.java` — unchecked-виняток із зрозумілим текстом;
- `lab/dto/` — records `ChatRequest`, `ChatMessage`, `ChatResponse`, лише формат API Ollama;
- `lab/Main.java` — два питання з історією розмови, час кожної відповіді в мс;
- `OllamaClientTest` — 5 тестів на `com.sun.net.httpserver.HttpServer` з портом 0, без Ollama.

Тести:

3. сервер мовчить 2 с при таймауті 300 мс → «не відповіла»;
4. невалідний JSON;

### Що побачив у відповідях

- **Історія розмови працює.** Друга відповідь починається з «the user previously asked for an explanation of semantic search in three sentences», тобто модель отримала перше питання і свою відповідь через `messages`.
- **Роздуми знову потрапили в `content`.** Як і в лабі 1 з `think: false`, перед відповіддю йдуть міркування англійською до `</think>`. Через це в історію пішов увесь цей текст, і промпт другого запиту став набагато довшим. Імовірно, саме тому друге питання, хоч і «коротше», тривало довше (415 с проти 283 с). Точно не заміряв, бо клієнт не повертає `prompt_eval_count`.
- **Мова відповіді.** Питання було українською, але модель довго вирішувала в роздумах, якою мовою відповідати, і обидва рази відповіла англійською. Без системного промпту мова відповіді не контролюється.

## Що пішло не так і як виправив

1. **`NoClassDefFoundError: com/fasterxml/jackson/databind/ObjectMapper` під час запуску `Main`.** `mvn test` проходив, а запуск з IDEA падав: у classpath були `jackson-core` і `jackson-annotations`, але не `jackson-databind`. Maven → Reload не допоміг, допоміг лише **File → Invalidate Caches** з перезапуском IDEA. Висновок: IDEA тримає власну копію налаштувань Maven-проєкту, і вона може розійтися з `pom.xml`. Еталонний запуск — через `mvn`.
2. **Невідомі поля у відповіді.** Ollama повертає в `message` ще поле `thinking`, а у відповіді — `done`, `load_duration` та інші. Без `@JsonIgnoreProperties(ignoreUnknown = true)` на `ChatResponse` і `ChatMessage` Jackson падає на першому ж невідомому полі. Додав анотацію в обидва records, бо поле `thinking` бачив ще в лабі 1.
3. **snake_case у JSON.** Поля `total_duration` і `eval_count` у Java назвав `totalDuration` і `evalCount` і прив'язав через `@JsonProperty`.
4. **Пакет.** У правилах проєкту для лаб записано `lab02`, у `LABS.md` — `lab`. Лишив `lab`, як у завданні лаби.

## Висновки

1. Для застосунку виклик LLM — звичайний HTTP POST із JSON, без жодної «магії». Вистачає `HttpClient` із JDK і Jackson.
2. Таймаутів потрібно два. `connectTimeout` (5 с) швидко показує, що сервер недоступний. Таймаут на запит має бути великим (у мене 10 хв), бо відповідь моделі на CPU займає хвилини.
3. Усі технічні збої (з'єднання, таймаут, статус, JSON) перетворюю на один виняток із людським повідомленням. Користувач бачить одне зрозуміле речення, а не stack trace.
4. Клієнт можна повністю протестувати без моделі: фейковий `HttpServer` на порту 0 перевіряє і успіх, і всі види збоїв за 3,4 с.
5. Модель не пам'ятає розмову: історію клієнт щоразу надсилає сам. Якщо разом з відповіддю зберігати роздуми моделі, контекст росте марно.
6. Без системного промпту `qwen3:4b` сама обирає мову відповіді і обрала англійську на українське питання.

## Що це дає Pastline і диплому (підрозділ 3.1.1)

- **AI-виклик як мережевий I/O.** У Pastline виклик моделі стоїть за портом (`EmbeddingModelPort` і аналогічний для генерації) з таймаутами, обробкою недоступності й власним доменним винятком. Помилку провайдера API Pastline має показувати зрозумілим кодом, а не 500 зі stack trace.
- **DTO провайдера не потрапляють у домен.** Records `ChatRequest` і `ChatResponse` описують формат Ollama, а для хмарного профілю OpenAI формат інший. Перетворення відбувається в адаптері.
- **Вимоги до генерації відповідей:**
  - системний промпт із мовою відповіді і правилом «лише з наданих записів»;
  - перед збереженням чи показом прибирати роздуми до `</think>`;
  - не тягнути їх в історію;
  - показувати відповідь потоком.
- **Тестування.** Інтеграцію з моделлю тестую без моделі, на фейковому сервері. Той самий підхід (WireMock чи `HttpServer`) застосую в застосунку.

## Питання, на які відповідаю без нотаток

**Де налаштовується таймаут і чому саме там?**
Таймаут з'єднання задаю на `HttpClient` (`connectTimeout`): він спільний для всіх запитів і стосується лише встановлення TCP-з'єднання. Таймаут очікування відповіді задаю на конкретному `HttpRequest` (`.timeout(...)`), бо різні запити можуть мати різний ліміт: генерація тексту триває хвилини, а embeddings — секунди. Якщо переплутати, клієнт або чекатиме вічно на мертвий сервер, або обриватиме нормальні довгі відповіді.

**Чому DTO провайдера не повинні потрапляти в доменний код Pastline?**
DTO відображають формат конкретного API: snake_case, поля `thinking`, `done`, структура `messages`. Якщо домен залежить від них, зміна версії Ollama чи перехід на OpenAI зачепить увесь застосунок. Домен працює зі своїми типами через порт, а перетворення живе в одному адаптері, який легко замінити й протестувати.

**Чим streaming-відповідь відрізняється для клієнта?**
Замість одного JSON приходить потік рядків (NDJSON). Клієнт читає їх построково (`BodyHandlers.ofLines()`), розбирає кожен, збирає `content` і завершує на `done: true`. Таймаут на всю відповідь тут не підходить. Потрібен таймаут на паузу між шматками, і окремо треба обробляти обрив посередині.

**Чому `HttpConnectTimeoutException` ловлю раніше за `HttpTimeoutException`?**
Бо він її підклас. Якщо спершу зловити батьківський клас, гілка для підкласу стане недосяжною, і компілятор видасть помилку. До того ж я не зміг би розрізнити «не під'єдналися» і «під'єдналися, але не дочекалися відповіді».

**Навіщо в `catch (InterruptedException)` викликати `Thread.currentThread().interrupt()`?**
Перехоплення `InterruptedException` скидає прапорець переривання потоку. Якщо його не відновити, код вище за стеком не дізнається, що потік просили зупинитись: наприклад, під час завершення застосунку чи скасування задачі.
